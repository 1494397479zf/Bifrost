# DTS 数据校验机制完整技术总结

> 本文档涵盖 DTS Comparator 的核心机制: Checkpoint、分块、CRC 算法、Delta 增量、分布式锁、一致性位点推进等。

---

## 一、整体架构

### 1.1 校验流程概览

```
源库 (Source) ──────CRC计算──────┐
                                  ├──→ Checkpoint存储 → Delta对比 → 最终结论
目标库 (Destination) ───CRC计算──┘
```

**核心组件**:
- **Comparator** (校验计算器): 在源库计算 CRC + 行数
- **Sinker** (校验应用器): 在目标库重新计算 CRC,对比差异
- **Checkpoint表**: `__tencentdb__.checksum_<jobId>`

---

## 二、Checkpoint 机制 (位点管理)

### 2.1 什么是 Checkpoint?

**本质**: 数据校验的"时间戳标记",类似于 binlog 的 GTID/Position。

**作用**:
- 记录某个时间点的数据快照校验结果
- 支持增量校验(Delta)的计算基准
- 防止并发写入导致的数据不一致

### 2.2 Checkpoint 表结构

```sql
CREATE TABLE `__tencentdb__`.`checksum_<jobId>` (
  db             VARCHAR(64),       -- 数据库名
  tbl            VARCHAR(64),       -- 表名
  chunk          INT,               -- 分块编号 (0, 1, 2, ...)
  chunk_index    VARCHAR(200),      -- 使用的索引名称
  lower_boundary VARCHAR(1024),     -- 分块下界 (JSON格式)
  upper_boundary VARCHAR(1024),     -- 分块上界 (JSON格式)
  this_crc       VARCHAR(40),       -- 源库 CRC 值
  this_cnt       INT,               -- 源库行数
  master_crc     VARCHAR(40),       -- 目标库 CRC 值
  master_cnt     INT,               -- 目标库行数
  chunk_time     FLOAT,             -- 计算耗时(秒)
  ts             DATETIME,          -- 最后更新时间
  skipped_reason VARCHAR(200),      -- 跳过原因
  dst_statement  MEDIUMTEXT,        -- 目标端需要执行的 CRC SQL
  PRIMARY KEY (db, tbl, chunk)
);
```

**关键字段解析**:
- `chunk`: 分块 ID,从 0 开始递增
- `lower_boundary`/`upper_boundary`: 示例 `{"id": [1000]}` → `{"id": [2000]}`
- `this_crc`/`master_crc`: XOR CRC32 计算结果 (16进制字符串)
- `dst_statement`: Base64 编码的目标端 SQL

**代码位置**:
- 表创建: `comparator/checksum.go:78-106`
- 字段定义: `comparator/table.go:20-50`

## 三、分块策略 (Chunk Mechanism)

### 3.1 为什么要分块?

1. **避免大事务**: 一次性计算千万级数据会导致事务超时
2. **并发校验**: 多个 chunk 可并行计算
3. **故障恢复**: 支持断点续传
4. **动态调优**: 根据耗时自动调整 chunk 大小

### 3.2 分块算法

**默认大小**: `DEFAULT_CHUNK_SIZE = 1000` 行

**动态调整逻辑** (`comparator/table_logic.go:420`):
```go
func (t *CrcTableLogic) autoChunkSizeByCostTime(cost float64) {
    if cost < 0.1 {  // 耗时 < 100ms
        t.ChunkSize = min(t.ChunkSize * 2, 10000)  // 翻倍,最大 10000
    } else if cost > 1.0 {  // 耗时 > 1s
        t.ChunkSize = max(t.ChunkSize / 2, 100)    // 减半,最小 100
    }
}
```

**分块边界计算** (基于主键/唯一索引):
```sql
-- 第 0 块: [MIN, MIN + 1000]
-- 第 1 块: (1000, 2000]
-- 第 2 块: (2000, 3000]
-- ...
```

**示例** (`lower_boundary`/`upper_boundary`):
```json
{
  "chunk": 0,
  "lower_boundary": "{\"id\": [1]}",
  "upper_boundary": "{\"id\": [1000]}"
}
```

**代码位置**:
- 分块核心逻辑: `comparator/table_logic.go:300-450`
- 边界计算: `comparator/checksum.go:200-280`

## 四、CRC 校验算法 (核心!)

### 4.1 CRC 计算公式

**完整 SQL** (`comparator/checksum.go:311`):
```sql
COALESCE(
  LOWER(
    CONV(
      BIT_XOR(
        CAST(
          CRC32(
            CONCAT_WS('#', 
              `id`, `k`, CONVERT(`c` USING BINARY), 
              ISNULL(`id`), ISNULL(`k`)
            )
          ) AS UNSIGNED
        )
      ), 
      10, 16  -- 10进制转16进制
    )
  ), 
  '0'
)
```

**逐步拆解**:
1. **`CONCAT_WS('#', ...)`**: 将所有列值用 `#` 拼接成字符串
   - 示例: `1#hello#0#0` (id=1, k='hello', c为NULL)
   
2. **`ISNULL(col)`**: 记录 NULL 标记 (0/1)
   - 避免 `1#NULL` 和 `NULL#1` 冲突
   
3. **`CRC32(...)`**: 计算 32 位 CRC 校验值
   
4. **`BIT_XOR(...)`**: 对所有行的 CRC 值做异或运算
   - **关键性质**: `A XOR B XOR B = A` (可逆性)
   
5. **`CONV(... , 10, 16)`**: 转为 16 进制字符串
   - 示例: `123456789` → `75bcd15`

### 4.2 为什么使用 XOR?

**XOR 的可逆性**支持 Delta 增量计算:
```
CRC_new = CRC_old XOR Delta_CRC_added XOR Delta_CRC_deleted
```

**示例**:
```
原数据: row1, row2
CRC_old = CRC32(row1) XOR CRC32(row2) = A

新增 row3, 删除 row2:
CRC_new = A XOR CRC32(row3) XOR CRC32(row2)
```

**代码位置**:
- CRC SQL 生成: `comparator/checksum.go:311-380`
- NULL 处理: `comparator/checksum.go:250-270`

## 五、Delta 变更机制 (增量校验)

### 5.1 什么是 Delta?

**定义**: 两个 checkpoint 之间的数据变更。

**核心思想**:
- Checkpoint1 (T1 时刻) → CRC1
- 期间发生变更: +row3, -row2, ~row1
- Checkpoint2 (T2 时刻) → 重新计算 CRC2
- **对比 CRC1 vs CRC2 判断是否一致**

### 5.2 Delta 计算流程

**实际实现** (非 XOR 增量,而是**重新计算**):
```sql
-- 推进 checkpoint 时重新计算完整 CRC
SELECT BIT_XOR(CAST(CRC32(...) AS UNSIGNED)) 
FROM `db`.`table` 
WHERE id > lower_boundary AND id <= upper_boundary;
```

**为什么不用 XOR 增量?**
- Binlog ROW 模式下无法精准获取所有变更行
- 并发写入可能导致顺序不一致
- 重新计算更简单可靠

### 5.3 Checkpoint 推进策略

**频率**: 每 **1 分钟** 推进一次 checkpoint

**目的**:
1. 处理增量数据
2. 缩小校验窗口
3. 减少误报

**实现逻辑**:
```go
// comparator/comparator.go
ticker := time.NewTicker(60 * time.Second)
for {
    select {
    case <-ticker.C:
        // 重新计算所有 chunk 的 CRC
        updateCheckpoint(ctx, conn, jobId)
    }
}
```

**代码位置**:
- Checkpoint 推进: `comparator/comparator.go:150-200`
- 增量处理: `comparator/checksum.go:400-450`

## 六、分布式锁机制 (高可用保障)

### 6.1 MySQL Lease (乐观锁)

**实现文件**: `library/lease/mysql.go`

**核心表**:
```sql
CREATE TABLE `argo_lease`.`task_lease` (
  job_id   VARCHAR(128),
  task     VARCHAR(128),  -- dumper/river/loader/sinker/checker
  plat     VARCHAR(32),   -- NewDTS
  hostname VARCHAR(256),  -- Pod 名称
  updated_at DATETIME,
  PRIMARY KEY (job_id, task, plat)
);
```

**加锁 SQL** (乐观锁):
```sql
UPDATE `argo_lease`.`task_lease` 
SET hostname = 'dts-xxx-pod', updated_at = NOW()
WHERE job_id = 'dts-12345' 
  AND task = 'comparator' 
  AND hostname IS NULL;  -- 关键: 只有 NULL 时才能抢锁
```

**解锁 SQL**:
```sql
DELETE FROM `argo_lease`.`task_lease`
WHERE job_id = 'dts-12345' AND task = 'comparator';
```

**特点**:
- ✅ 轻量级,无需额外组件
- ✅ 适合短任务
- ❌ 无心跳机制,节点宕机需手动清理

**代码位置**: `library/lease/mysql.go:40-120`

### 6.2 Etcd Lease (分布式锁)

**实现文件**: `library/lease/etcd.go`

**核心机制**:
1. **申请 Lease**: `Grant(TTL=60s)`
2. **心跳续约**: 每 `10s` 发送 KeepAlive
3. **自动过期**: 60s 内未续约则 Lease 失效,自动释放锁
4. **主动检测**: Lease 过期后主动退出进程

**代码示例**:
```go
// 申请锁
lease, err := etcdClient.Grant(ctx, 60)
session, err := concurrency.NewSession(client, 
    concurrency.WithLease(lease.ID))

// 心跳协程
go func() {
    ticker := time.NewTicker(10 * time.Second)
    for {
        select {
        case <-ticker.C:
            _, err := etcdClient.KeepAliveOnce(ctx, lease.ID)
            if err != nil {
                qlog.Fatal("Lease expired, exit")
                os.Exit(1)
            }
        }
    }
}()
```

**对比 MySQL Lease**:
| 特性 | MySQL Lease | Etcd Lease |
|------|------------|------------|
| 实现方式 | 乐观锁 (UPDATE WHERE) | 分布式锁 + 心跳 |
| 心跳机制 | ❌ 无 | ✅ 10s 一次 |
| 故障检测 | ❌ 手动清理 | ✅ 自动过期 |
| 适用场景 | 短任务 (< 5min) | 长任务 (持续运行) |

**代码位置**:
- Etcd 实现: `library/lease/etcd.go:30-200`
- 心跳逻辑: `library/lease/etcd.go:120-150`

## 七、一致性位点推进 (Binlog Position)

### 7.1 什么是一致性位点?

**定义**: 保证源库和目标库数据一致性的 binlog 坐标。

**核心字段**:
- **GTID**: `3E11FA47-71CA-11E1-9E33-C80AA9429562:1-5`
- **Binlog File + Position**: `mysql-bin.000003:120`

### 7.2 位点推进流程

**River 组件** (`dts/river/river.go`):
```go
// 1. 读取 binlog 事件
for event := range binlogStream {
    // 2. 解析 DML/DDL 事件
    dmlEvent := parseDMLEvent(event)
    
    // 3. 应用到目标库 (Sinker)
    sinker.Apply(dmlEvent)
    
    // 4. 更新 checkpoint
    saveCheckpoint(event.GTID, event.Position)
}
```

**Checkpoint 存储**:
```sql
CREATE TABLE `__tencentdb__`.`river_checkpoint` (
  job_id      VARCHAR(128),
  gtid_set    TEXT,           -- GTID 集合
  binlog_file VARCHAR(255),   -- binlog 文件名
  binlog_pos  BIGINT,         -- binlog 位置
  updated_at  DATETIME,
  PRIMARY KEY (job_id)
);
```

### 7.3 断点续传机制

**启动时恢复**:
```go
// 1. 读取最后的 checkpoint
checkpoint := loadCheckpoint(jobId)

// 2. 从该位点继续消费 binlog
binlogStream := mysql.StartReplication(
    GTIDSet: checkpoint.GTIDSet,
    BinlogFile: checkpoint.BinlogFile,
    BinlogPos: checkpoint.BinlogPos,
)
```

**各组件的断点续传**:
| 组件 | 断点信息 | 存储位置 |
|------|---------|---------|
| Dumper | 已导出的表列表 | COS + DB |
| River | Binlog Position/GTID | DB 表 |
| Loader | 已导入的 SQL 文件 | COS 清单 |
| Sinker | Kafka Offset | Kafka 内部 |
| Comparator | Chunk 编号 | Checksum 表 |

**代码位置**:
- River checkpoint: `binlog/river/river.go:200-250`
- Dumper checkpoint: `dumper/dump/mydumper.go:300-350`

## 八、完整校验流程示例

### 8.1 初始全量校验

**Step 1: Comparator 计算源库 CRC**
```sql
-- chunk 0: id ∈ [1, 1000]
INSERT INTO `__tencentdb__`.`checksum_dts-12345` 
  (db, tbl, chunk, chunk_index, lower_boundary, upper_boundary, this_crc, this_cnt)
VALUES 
  ('mydb', 'users', 0, 'PRIMARY', '{"id":[1]}', '{"id":[1000]}', 'a1b2c3d4', 1000);
```

**Step 2: Sinker 在目标库重新计算**
```sql
-- 读取 dst_statement (Base64编码的SQL)
SELECT 
  COALESCE(LOWER(CONV(BIT_XOR(...), 10, 16)), '0') AS crc,
  COUNT(*) AS cnt
FROM `mydb`.`users`
WHERE id >= 1 AND id <= 1000;

-- 更新 master_crc 和 master_cnt
UPDATE `__tencentdb__`.`checksum_dts-12345`
SET master_crc = 'a1b2c3d4', master_cnt = 1000
WHERE db = 'mydb' AND tbl = 'users' AND chunk = 0;
```

**Step 3: 对比结果**
```sql
-- 查询不一致的 chunk
SELECT db, tbl, chunk, this_crc, master_crc, this_cnt, master_cnt
FROM `__tencentdb__`.`checksum_dts-12345`
WHERE (this_crc != master_crc) OR (this_cnt != master_cnt);
```

### 8.2 增量 Delta 校验

**场景**: 全量校验期间,源库持续写入。

**推进 Checkpoint**:
```
T0 时刻: Chunk 0 校验完成 → CRC = a1b2c3d4, cnt = 1000
T1 时刻: (60s后) 新增 5 行,删除 2 行
         → 重新计算 CRC → b5c6d7e8, cnt = 1003

对比: a1b2c3d4 != b5c6d7e8 → 标记为不一致
```

**处理策略**:
1. **允许窗口**: 对比最近 2 个 checkpoint 之间的差异
2. **延迟确认**: 等待 binlog 同步完成后再次校验
3. **人工介入**: 超过阈值则告警

## 九、高级特性

### 9.1 采样校验 (CrcMode=Sample)

**场景**: 超大表 (亿级) 全量校验耗时太长。

**策略**: 随机抽样 10% 的 chunk 进行校验。
```go
if crcMode == "Sample" && rand.Intn(100) < sampleRate {
    // 跳过当前 chunk
    skipChunk(ctx, chunk)
}
```

**代码位置**: `comparator/table_logic.go:500-520`

### 9.2 空表优化

**跳过条件**:
```sql
-- 源库和目标库都为空
this_cnt = 0 AND master_cnt = 0
→ skipped_reason = 'EmptyTable'
```

**代码位置**: `comparator/checksum.go:150-170`

### 9.3 只校验行数 (CrcMode=RowsCount)

**适用场景**: 
- 数据一致性要求不高
- 追求极致性能

**实现**:
```sql
SELECT COUNT(*) AS cnt FROM `db`.`table` 
WHERE id > lower AND id <= upper;
```

**代码位置**: `comparator/table_logic.go:350-370`

## 总结

| 机制 | 核心作用 | 关键技术 |
|------|---------|---------|
| **Checkpoint** | 时间点快照 | Binlog Position/GTID |
| **分块 (Chunk)** | 大表拆分 | 主键范围分割 + 动态调优 |
| **CRC 算法** | 数据指纹 | BIT_XOR + CRC32 |
| **Delta 增量** | 变更检测 | 重新计算 CRC (非 XOR 增量) |
| **MySQL Lease** | 任务互斥 | 乐观锁 (UPDATE WHERE hostname IS NULL) |
| **Etcd Lease** | 高可用锁 | 分布式锁 + 心跳续约 |
| **位点推进** | 断点续传 | GTID Set + Checkpoint 表 |

这套机制保证了 DTS 在**高并发、大数据量、长时间运行**场景下的数据一致性校验能力! 🚀
