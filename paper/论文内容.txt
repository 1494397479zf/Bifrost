 I 华 中 科 技 大 学 硕 士 学 位 论 文 
 
摘  要 
数据迁移，又称之为数据移植，是指从一种数据环境（源数据库）中提取数据，
根据需要迁移或移植到另一种数据环境（目标数据库）中； 目前数据迁移除了基本
的数据复制功能，还需要实现数据订阅功能以及基于数据迁移与数据订阅功能的多
样化需求。  
当前研究 设计的数据迁移中间件，主要包含数据迁移与数据订阅两大功能模块，
数据迁移模块又主要分为全量迁移（将源端数据库所有数据进行迁移）与增量迁移
（将源端数据库产生的数据更新在目标端进行回放）。其中全量迁移能够实现数据
在异构数据库之间的高速复制，完全能够满足现有的数据异地备灾等功能需求；增
量迁移能够实现数据实时同步，主要应用于数据的不停服迁移等市场需求，但是随
着互联网产业的发展，对于增量迁移的实时性提出了更高的要求，从而衍生出了数
据的异地多活等更复杂的增量迁移需求；数据订阅功能指的是将数据信息封装成消
息存放在一个消息队列中，让消费者可以自由消费消息队列中的消息，从而实现生
产者与消费者的解耦，提高系统工作效率，主要可以应用在目前的异步消息通知、
应用缓存更新等方面。  
本文实现的异构数据库迁移中间件也同时实现了这三个主要的功能，包括全量
数据迁移，增量数据迁移，数据订阅；能够满足类似 不停服数据迁移、数据异地灾
备、异地多活 (单元化 )、跨境数据同步、实时数据仓库、查询报表分流、缓存更新、
异步消息 通知等功能 。 
 
关键词： 数据迁移     数据订阅     全量迁移     增量迁移

Abstract  
Data migration, refers to extracting data from a data environment (source database), 
migrating to another data environment (target database) as needed. Currently data 
migration needs to implement data subscription capabilities and d iverse needs based on 
data migration and data subscription capabilities in addition to move data from a database 
to another.  
The data migration middleware currently researched and designed mainly includes two 
major functional modules: data migration and da ta subscription. The data migration module is 
mainly divided into full migration (migrating all data from the source database) and 
incremental migration (update the data generated by the s ource database to the target  for 
playback).The full -scale migration can realize high -speed replication of data between 
heterogeneous databases, which can fully meet the functional requirements of existing data 
off-site disaster recovery; incremental migration can realize real -time data synchronization, 
and is mainly applie d to markets such as data non -stop migration, but with the development of 
the Internet industry, higher requirements are imposed on the real -time nature of incremental 
migration  which leads to more complex incremental migration requirements such as remote 
data sharing. Data subscription function refers to encapsulate data information into messages 
in a message queue so that consumers can freely consume the messages in the message queue, 
with this function  we can improve  the system work efficiency  and decoup le between the 
producer and the consumer  and mainly applicable to the asynchronous message notification 
and Cache updates and more.  
The heterogeneous database migration middleware implemented in this paper also 
implements these three main functions, includ ing full data migration, incremental data 
migration, and data subscription so that can achieve these functions such as non -stop data 
migration, data offsite disaster recovery, and live offsite, cross -border data synchronization, 
real-time data warehouse, q uery report offload, cache update, asynchronous message 
notification and more.  
 
Key words  ：Data migration    Data subscription    Full migration    Incremental migration

 1 华 中 科 技 大 学 硕 士 学 位 论 文 
 
1  绪论  
1.1  研究背景  
随着信息技术的迅猛发展以及 信息数据量的海量增长 ，大多数企业都开始 借助
多样化的软件来减轻业务压力 、缩小企业 成本进而提升企业效益 ，但是随着软件应
用愈加广泛以及市场需求的多样性，软件需要不停地推出新的解决方案 来解决市场
提出的问题 ，“中间件 ”的概念便 应运而生[1]。从古老的 C/S三层架构到现在被大多数
互联网公司广泛应用的分布式系统，不同系统间的 通信与数据传递就成了瓶颈 ，而
中间件不仅仅解决了硬件 差异与通信方式、 协议不同的问题 ，甚至可以 适配不同操
作系统，使得上层应用的开发和维护成本被大大降低， 企业效益大大提升[2]。 
互联网飞速发展的 衍生物是软件业务规模的海量增长 以及与日俱增的数据压
力，随着互联网高速发展 、越来越多高新技术逐渐融入寻常百姓的生活 ，数据量也
进入了爆炸式增长阶段，由于这些数据 的存在会对社会经济发展以及 国家治安管理
都产生重大影响 ，世界各国都把推进 经济数字化作为实现创新发展的重要衡量标准
[3]。进而更加推动了全球互联网产业与技术的发展 并导致互联网应用数量呈现 “井喷 ”
式增长， 花样繁多的互联网应用会产生海量的异构数据，同时由于新兴的 “互联网 +”
概念的火热 传播，各传统企业也 纷纷将各自业务与互联网挂钩，利用智能传感设备
或者移动设备 大量采集 用户行为数据 ，进而衍生出与人们生活工作 联系更加紧密的
云办公、云购物等极大改变人们生活方式的智能服务， 而这些服务产生的 数据被称
为非关系型数据[4]。 
非关系型数据库的发展与近年来互联网产业的飞速发展脱不开关系，随着数据
量愈加庞 大，传统关系 型数据库在存储容量、水平扩展、解决分布式问题上都显得
无能为力，也就刺激了非关系型数据库的产生 。非关系型数据库 的存储方式多种多
样，以文件存储或者列存储、图存储等 方式为主 ，由于其能够在大规模廉价的集群
上存储这一高可扩展特性而深受 用户与企业的喜爱[5]。所以目前大部分企业都会选择
适合自身的方式将工作重心由传统关系型数据库转变为搭建互联共享的云平台存储
与办公环境 ，并为类似于 Hadoop的大数据分析平台提供基础数据支持[6]。

1.2  研究的意义  
一个功能强大的数据迁移中间件能够解决目前互联网架构的许多问题：  
（1）数据的冷备份  
数据可能会因为各种人为或者天灾等因素面临丢失或者被破 坏的风险，人为因
素例如数据库管理人员的误操作或网络黑客的攻击等，自然因素例如存储设备老化
故障或者地震等不可抗力造成存储介质的损坏[8]。为了避免这种风险， 就需要对数据
进行冷备份 。 
伴随着服务器海量数据的不断增长，数据体积变得越来越庞大，这时再进行数
据备份与数据恢复 速度就会变得尤为重要，假设过亿的数据体量进行备份，会对数
据库产生巨大的压力，数据如果不慎丢失恢复起来又需要很长的时间，数据恢复的
这段时间用户就不能使用，这就对数据备份与恢复速度提出了更高的要求 ，传统的
数据备份方式就无法胜任现在的需求，这时候 高效、安 全、高速的数据迁移中间件
就成了企业与用户的选择[9]。

新的机房，异地多活具备在生产环境上进行灰度的能力。同时对用户进行分流以缓
解服务器的压力也是 目前加快服务响应时间的重要方式，许多公司采用了异地多活

以应用在如下几个典型的场景中。  
（1）数据发布与订阅  
数据发布与订阅 也称之为配置中心服务 ，简单说就是用户将信息发布到
Zookeeper 节点上，然后不同用户都可以在这个节点上订阅发布者发布的消息，这样
消费者用 户能够动态获取发布者用户的有效信息，从而实现配置中心的一种动态 数
据更新以及用户数据的集中式管理[22]。 
在日常的开发工作中，经常会使用到一些通用的配置信息， 这些信息一般 具有
数据量较小、内容动态变化、在各机器上共享一致等特征，对于这样的数据开发者
就可以发布到 Zookeeper 节点上，让共享配置的机器去订阅该节点上的消息，从而减
轻开发人员压力并且保证共享配置的正确性[23]。一般数据发布与订阅有推模式和拉
模式两种  ： 
① 推： Zookeeper 节点主动将数据更新发送到所有的订阅者 。 
② 拉：订阅用户主动请求 Zookeeper节点下发 最新的数据更新，工作节点不会
将数据更新推送给未发出请求的订阅者 。 
Zookeeper 的数据发布 /订阅采取的是更为巧妙的推拉结合方式， 即工作节点将数
据更新的消息推送给订阅者，由订阅者决定是否主动去获取具体 变更数据。

经常与 Kafka消息队列一起被提出的概念有 “生产者消费者模式 ”， 生产者消费者

消费者 API：支持消费者信息 订阅以及信息流处理。 
Stream API ：将输入流转换为输出流，并产生结果。  
Connector API ：执行可重用的生产者和消费者 API，可将 Topic链接到现有的应

2.3  RPC 通信协议  
2.3.1  RPC 通信协议概述  
远程过程调用即开发者常说的 RPC（Remote Procedure Call ），实质上 是一个计
算机通信协议。 该协议的主要目的是方便程序员通过一台计算机上的程序 通过 RPC
调用另一台计算机上的程序 。 
在目前各大互联网公司都使用分布式系统的前提下，应用服务的各个组件可能
被部署在不同的服务器上，各个组件之间的低延时通信就成为了保证应用服务良好
体验的关键， RPC的实现其实可以基于传统的 HTTP协议， HTTP协议由于其良好
的跨平台通用特性 被广泛应用于目前常见的 B/S架构产品，但是由于其传输数据 报
头较长导致性能比较差[33]。所以随着 RPC通信协议的成熟 ，分布式系统的构建就更
加容易，极大推动了当前大数据环境下分布式系统的发展并为其扩展性和容错性提
供了技术保障 。 
2.3.2  RPC 通信协议优势  
相比于传统的 Http通信，使用 Rpc通信的理由也非常 简单，在目前的分布式系
统架构的基础上，系统之间的通信需要一个更加便捷、更加轻量级、更加快速响应
的方式， Rpc恰恰能够满足这些需求。

3  中间件分析与设计  
3.1  需求分析  
从中间件的使用角度，用户分为三类，一类为管理员，一类为私有用户，最后
一类为公共用户；管理员用户具有最高管理权限，能够管理所有注册用户，同时能
够管理所有注册用户的任务、配置任务失败报警人员信息；私有用户拥有自己的执
行服务器，能够查询并管理自己配置的任务，配置自己任务的报警人员信息；公共
用户任务在共有服务器上执行，能够查询并管理自己配置的任务，配置自己任务的
报警人员信息。  
从中间件实现角度， 中间件主要需求由功能需求与性能需求组成，本节就从这
两个角度进行分析。  
3.1.1  功能需求分析  
（1）预检查  
在任务成功创建后， 需要进行一定的检查来确保任务能够顺利执行的，这些检
查包括：  
① 执行节点与源端网络连通性检查。  
② 如果任务选择结构迁移，则需要检查用户提供的账户是否在目标端有建表等
相应的权限。  
③ 大小写适配检查，即用户设置的映射信息后是否勾选大小写适配，如果用户
勾选大小写适配， 则类似 Name与name这样的字段分别位于源端和目标端是可以通
过检查的，否则预检查就会报错。  
④ 双向复制检查，如 果用户选择开启双向复制，需要检查是否存在标志位以及
源端和目标端 列的类型。  
（2）结构迁移

① 任务开始前结构迁移，此时能够实现结构迁移的方式比较多，例如 手动在目

① 全量迁移的数据采集方式类似 于对源端做一个快照，然后根据主键的不同将

② 根据目前市场上主流的数据 库，中间件 的增量数据采集方案是根据数据日志

（4）数据过滤  
从源端提取的数据有些对于用户而言是无用的，比如用户只想迁移源端的部分
字段，或者只想订阅源端的部分字段，这时候需要对现有的数据进行过滤，即需要
支持用户自定义设置过滤字段，且这个字段的设置应该是在用户任务启动之前。假
设用户在任务过程中修改了过滤字段，由于之前产生的数据可能还未消费或者还未
在下游应用，这样不论是订阅任务还是迁移任务都会产生数据不一致情况甚至出现
错误，所以数据过滤条件 的设置一定是在任务启动之前，且会对数据迁移任务的全
量过程、增量过程以及校验过程全部生效，会对数据订阅任务的增量数据生效。  
（5）数据应用  
将数据进行提取、转换、过滤、封装后就需要对数据进行应用。为了实现异地
多活、线上 OLAP系统支持等越来越复杂的需求，既要 保证数据的正确性，同时又
要最大化减少数据迁移的延时，就需要更加合理与高效的高并发设计。

一个完整健全的 中间件除了能够实现这些必须的功能外，还需要对性能提出更

（1）安全性需求  
保证用户数据的安全也是 中间件的设计重点，目前 中间件通过以下几个方面的
设计来保证用户数据的安全性：  
① 访问控制策略： 数据迁移中间件采用租约制度，通俗来说就是分为公有与私
有的区别，公有即 所有共有用户任务在同一个服务器上或者同一个集群上执行，私
有即私有用户的任务是在单独的服务器或者集群上运行的且只运行此用户的任务，
每个用户登陆后只能看到自己的任务情况；同时用户可 以为自己的服务器设置白名
单，只有白名单的 IP地址所属设备才能访问。  
② 建议用户通过内网访问服务器部署实例，可以使服务器免受 DDoS攻击的风
险。  
③ 若用户选择对外开放，当 中间件认为用户实例正在遭受 DDoS攻击时，会首
先启动流量清洗功能，即当监测的 PPS（Package Per Second ）或者 BPS（Bits Per 
Second）过高或者每秒新建并发连接、非并发连接过高就会进行流量清洗，处于流
量清洗状态下的应用实例可以正常访问。  
（2）可靠性需求  
数据的可靠性是数据库迁移中间件的必要条件，如果数据在迁移过程中产生了
丢失或者损坏，那对于企业来说会造成灾难性的后果，为此 中间件也进行了多种设
计来保证数据可靠性：  
① 进行全量或者增量迁移的任务会实时上报迁移进度并落库，当服务器宕机时
能够找到位置点进行恢复。  
② 迁移任务实现采取幂等操作，在任务恢复时能保证数据结果的一致性。  
③ 任务结束时有可选择的校验选项来保证任务结果的正确性。

ExtractTask 的生成逻辑为：  
1）表的主键为 int类型，则将源端数据进行 chunk分区，每个 chunk对应一个
task， 每个 chunk的数据量按照主键差值至少跨 100，0000。 单表的分区数最大为 1024。
即int型主键分区的逻辑为：  
（1）查询源表主键最大值 maxPkValue ，主键最小值 minPkValue ，totalSize = 
maxPkValue - minPkValue ，默认分区 chunk = 1000000 ； 
（2）计算分区数 taskCount = Math.ceil(tot alSize / chunkSize) ，若 taskCount > 
1024，则调整 chunkSize = Math.ceil(totalSize / 1024) ，taskcount = 1024 ； 
（3）以taskCount 和chunkSize 对源表进行切分，则切分为类似 [minPkValue ，
minPkValue + chunkSize - 1]，[minPkValue + chunkSize ，minPkValue + 2 * chunkSize - 
1]......[minPkValue + n * chun kSize，maxPkValue] 。 
2）表的主键不为 int类型，查询最小最大值为 minPkValue ，maxPkValue ，生成
的ExtractotTask 起始点为 [minPkValue ，maxPkValue] 。

（1）全量数据未拉取完全  
（2）全量导入过程出错

（6）源端和目标端编码不同  
（7）目标端在迁移前或者迁移过程中新增数据  
有效的检测出全量和增量中产生的数据不一致，是数据校验功能的设计目标。

3.7  结构迁移设计

（2）特殊目标端的适配，如 GP，DDB的均衡字段的问题， Kudu不支持二级索

（3）目标端权限检查需要检查建表、建库权限

目标数据库的语法）记录在 Event的RowChange 当中，随后由 EventGraphManager
进行处理。  
（3）EventGraphManager 不断从 EventQueue 中获取到 Event，根据该事件中所
有涉及的主键和唯一性索引构建 EventGraph ，然后放入到对应的所有的 EventGraph
中， 计算其入度， 如果在所有依赖图中的入度为 0， 根据热定选择策略启动一个 Worker
放入线程池中执行，或者直接放入 slaveQueue 中等待其他 worker执行。  
（4）每个 Worker都是一个 Runnable ，根据中间件设置的并发数初始化放入到
一个 workerQueue 中，当 EventGraph 中存在入度为 0的Event。判断 WorkerQueue
是否有闲置的 Worker，如果存在取出这个 worker绑定这个 Event放入到线程池中执
行，如果不存在就放到 salveQueue 中。

5  总结与展望  
5.1  全文总结  
基于上述的几章讲解，本文先从数据迁移中间件的开发背景讲起，分析了当下快
速增长的海量互联网数据对于中间件提出的类似不停服数据迁移、数据异地备灾、
异地多活以及提供线上 OLAP系统新的解决方案等需求。  
紧接着讲述了在 中间件中采用的一些关键技术，如 Zookeeper 主要用于 中间件中
center与engine的心跳检测、 engine工作汇报等；如 Kafka在大的功能模块上提供数
据订阅的功能，在小的功能模块上为一推多拉、任务结构迁移提供更优选择的解决
方案；如 Rpc通信用于在 dashBoard 与center的数据通信以及 center与engine的数
据通信来降低 中间件的响应延迟提升用户的使用体验等。  
第三章通过功能需求分析与性能需求分析两个方面初步讲解了 中间件需要具备
的能力以及为什么需要设计这些能力。紧接着就 中间件的各个设计模块进行了详细
的设计与实现，为了使读者能够更容易理解，讲解的顺序也是以任 务流程顺序为基
础的，首先从 center控制中心的设计，主要讲解了 center基本的 API以及任务下发
流程的优化；其次就来到了 engine执行节点的设计，这部分包含的内容比较多，首
先对 engine的专有名词进行了说明，再从 engine最上层调用流程为切入点，进而结
合engine的常用 API为大家介绍了 engine内部的组件以及它们的功能；进而更加深
入地介绍 中间件主要功能 “全量迁移 ”与“增量迁移 ”的实现细则。 紧接着 将这两个主要
功能中的三个公有模块 “结构迁移 ”、 “Applier” 与“数据校验 ”提取出进行单独讲解 ，
三个章节都从设计方案、执行流程与细节方面对功能实现进行了进一步诠释，全文
在讲解完主要功能后进入尾声，每一步设计的目的都是为了功能更好地实现以及用
户更好的体验。
