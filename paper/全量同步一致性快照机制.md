# DTS 全量同步一致性快照机制

> 本文档详细介绍 DTS Dumper 的 FTWRL + 一致性快照机制,涵盖加锁流程、子线程快照建立、解锁时机等核心实现。

---

## 一、核心概念

### 1.1 什么是一致性快照?

**定义**: 在某个时间点 T1,通过加锁机制冻结数据库状态,然后建立事务快照,保证后续读取的数据都是 T1 时刻的一致性视图。

**核心目标**:
- 保证全量数据导出的一致性
- 协调 InnoDB (MVCC) 和 MyISAM (表锁) 的不同特性
- 最小化锁持有时间,减少对业务的影响

### 1.2 为什么需要 FTWRL?

**场景**: DTS 需要同时导出 InnoDB 和 MyISAM 表,并保证:
1. 所有表的数据对应同一个 binlog 位点
2. 导出期间数据不被修改
3. 支持并发导出提升性能

**挑战**:
- InnoDB 支持 MVCC,可以通过 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 建立快照
- MyISAM 不支持事务,只能通过表锁保证一致性
- 需要一个"全局时刻"来协调两种引擎

**解决方案**: `FLUSH TABLES WITH READ LOCK` (FTWRL)
- 全局读锁,阻塞所有写操作
- 在该锁下建立 InnoDB 快照 + MyISAM 表锁
- 释放全局锁,各线程继续持有自己的快照/表锁

## 二、完整加锁流程

### 2.1 时序图

```
时间轴:
T0 ──────── T1 ──────── T2 ──────── T3 ──────── T4 ───────→

主线程:
T0: FLUSH TABLES WITH READ LOCK;       // 加全局读锁 (阻塞所有写操作)
T1: START TRANSACTION WITH CONSISTENT SNAPSHOT;  // 主线程开启快照
    SHOW MASTER STATUS;                // 记录 binlog 位点

子线程 (InnoDB):
T1: [并发启动]
    SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
    START TRANSACTION WITH CONSISTENT SNAPSHOT;  // 子线程开启快照
    
子线程 (MyISAM):
T1: LOCK TABLES `db1`.`tbl1` READ, `db1`.`tbl2` READ, ...;  // 锁各自的表

主线程:
T2: UNLOCK TABLES;  // ✅ 释放全局锁 (此时数据已被快照/表锁保护)

所有线程:
T2-T4: SELECT * FROM ... WHERE ...;  // 并发导出数据
       
清理:
T4: UNLOCK TABLES;  // MyISAM 解锁
    COMMIT;         // InnoDB 提交事务
```

### 2.2 主线程执行流程

**文件**: `dumper/dump/mydumper.go:195-240`

```go
// 1. 如果是全量+增量迁移,先加全局读锁 (FTWRL)
if common.HasDataAndIncrementMigrate(t.cfg.Opt.MigrateType) {
    if err = lockdumper.GlobalLock(); err != nil {
        return err
    }
    lockdumper.status.GlobalLocked = true
}

// 2. 主线程设置事务隔离级别为 REPEATABLE READ
if _, err = t.conn.ExecContext(t.ctx, config.SetSessRepeatableRead); err != nil {
    return err
}

// 3. 主线程开启一致性快照事务 (START TRANSACTION WITH CONSISTENT SNAPSHOT)
// 注释说明: 不能在锁表时开启事务,因为会隐式释放已持有的读锁
if _, err = t.conn.ExecContext(t.ctx, config.StartTrxSnapshot); err != nil {
    return err
}

// 4. 记录 binlog 位点 (T1 时刻)
if common.HasIncrementMigrate(t.cfg.Opt.MigrateType) {
    pos, err = dbwork.GetBinlogPos(t.ctx, t.conn, t.cfg, false, config.BinlogPosT1)
    qlog.QInfoF(t.ctx, "BinlogPosT1: %s", pos.ToStoreContent())
}

// 5. 启动子线程并发导出
if err = lockdumper.Run(t.dbpool, t.databases); err != nil {
    return err
}
```

**关键说明**:
- **行 3-8**: 只有在全量+增量模式下才加 FTWRL
- **行 11-14**: 设置隔离级别为 REPEATABLE READ (RR)
- **行 17-20**: 开启一致性快照事务 (兼容 MySQL 4.1.8+)
- **行 23-26**: 记录 binlog 位点 (BinlogPosT1)
- **行 29-31**: 启动子线程并发导出

## 三、关键 SQL 定义

### 3.1 核心 SQL 语句

**文件**: `config/sql.go`

```go
// FTWRL 全局读锁
FlushTableWithReadLock = "FLUSH TABLES WITH READ LOCK;"

// 一致性快照事务 (兼容 MySQL 4.1.8+)
StartTrxSnapshot = "START TRANSACTION /*!40108 WITH CONSISTENT SNAPSHOT */;"

// 设置事务隔离级别
SetSessRepeatableRead = "SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;"

// 解锁
UnlockTables = "UNLOCK TABLES /* FTWRL */;"
```

**版本兼容性说明**:
- `/*!40108 ... */`: MySQL 注释语法
  - 版本 >= 4.1.8: 执行 `WITH CONSISTENT SNAPSHOT`
  - 版本 < 4.1.8: 忽略该子句,仅执行 `START TRANSACTION`

### 3.2 加锁/解锁实现

**文件**: `library/dbops/mysql_ops.go:939-960`

```go
// 加全局读锁
func (op *MySQLOpsContext) LockGlobalContext() error {
    var err error
    query := config.FlushTableWithReadLock  // FTWRL
    _, err = op.ExecContext(query)
    return err
}

// 解全局读锁
func (op *MySQLOpsContext) UnlockContext() error {
    var err error
    query := config.UnlockTables
    _, err = op.ExecContext(query)
    return err
}
```

## 四、子线程一致性快照建立

### 4.1 InnoDB 子线程初始化

**文件**: `dumper/executor/processor.go:262-320`

```go
func (t *DumperExecutor) InnodbDumpInit(opt map[string]interface{}) error {
    // 1. 设置超时时间
    _, err = t.conn.ExecContext(t.Context(), config.SetWaitTimeout)
    
    // 2. 设置时区
    _, err = t.conn.ExecContext(t.Context(), config.SetTimeZone)
    
    // 3. 设置字符集
    _, err = t.conn.ExecContext(t.Context(), config.SetNamesBinary)
    
    // 4. 设置事务隔离级别为 REPEATABLE READ
    _, err = t.conn.ExecContext(t.Context(), config.SetSessRepeatableRead)
    
    // 5. 【关键】开启一致性快照事务
    _, err = t.conn.ExecContext(t.Context(), config.StartTrxSnapshot)
    // SQL: START TRANSACTION /*!40108 WITH CONSISTENT SNAPSHOT */;
    
    // 6. 如果有 TokuDB 表,额外准备快照
    if tokuTbl != nil {
        err = dbops.PrepareTokuSnapShot(t.Context(), t.conn, tokuTbl)
    }
    
    return nil
}
```

**关键点**:
- **行 11-12**: 设置隔离级别为 RR (必须在开启事务前设置)
- **行 15-17**: 开启一致性快照,此时建立 Read View
- **行 19-21**: 特殊引擎 (TokuDB) 的额外处理

### 4.2 MyISAM 表的锁表处理

**文件**: `dumper/dump/lockstill.go:191-212`

```go
// MyISAM 子线程分别锁各自负责的表
func (t *lockstill) myisamLockToDump(xp *executor.ExecPool) error {
    // 广播锁表指令给所有 MyISAM 导出线程
    xp.Broadcast(dump_exec.LockMyisam, nil)
    err = xp.WaitBroadcast()
    if err == nil {
        qlog.QInfoF(t.ctx, "myisamLockToDump done")
    }
    t.status.MyisamLocked = true
    return err
}
```

**实际锁表 SQL**:
```sql
LOCK TABLES 
  `db1`.`tbl1` READ,
  `db1`.`tbl2` READ,
  ...;
```

**注意**:
- 每个子线程只锁自己负责的表,不是全局锁
- 一旦锁定,必须持续到数据导出完成

## 五、解锁时机 (关键!)

### 5.1 无备份锁模式 (MySQL < 8.0)

**文件**: `dumper/dump/lockstill.go:211-225`

```go
func (t *lockstill) runWithoutBackupLock(db *sql.DB, databases map[string]*st.DatabaseInfo) error {
    // 1. 初始化 InnoDB 子线程 (开启快照)
    err = t.innodbDumpInit(t.innodbDbPool)
    
    // 2. 初始化 MyISAM 子线程 (锁表)
    err = t.myisamDumpInit(t.myisamDbPool)
    
    // 3. MyISAM 表锁表
    err = t.myisamLockToDump(t.myisamDbPool)
    
    if t.status.GlobalLocked {
        // 【解锁时机】
        // - MyISAM 表已被子线程锁住 (LOCK TABLES READ)
        // - InnoDB 子线程已开启一致性快照事务
        // - 此时可以安全释放主线程的 FTWRL 全局锁
        err = t.dbOpsContext.UnlockContext()  // UNLOCK TABLES
        if err != nil {
            return err
        }
        t.status.GlobalLocked = false
    }
    
    // 4. 后续并发导出数据...
    return t.dumpData(db, databases)
}
```

**时序图**:
```
主线程:
  T0: FLUSH TABLES WITH READ LOCK;  ← 全局锁
  T1: START TRANSACTION ...;         ← 主线程快照
      [启动子线程]

子线程 (InnoDB):
  T1: START TRANSACTION ...;         ← InnoDB 快照建立 ✅

子线程 (MyISAM):
  T1: LOCK TABLES ... READ;          ← MyISAM 表锁建立 ✅

主线程:
  T2: UNLOCK TABLES;                 ← 释放全局锁 ✅
      (此时所有子线程的快照/表锁已建立)

所有线程:
  T2-T4: SELECT * FROM ...;          ← 并发导出数据
```

### 5.2 有备份锁模式 (MySQL 8.0+ / Percona)

**文件**: `dumper/dump/lockstill.go:313-355`

**备份锁 SQL**:
```sql
-- MySQL 8.0+ 引入的轻量级备份锁
LOCK INSTANCE FOR BACKUP;
```

**优势**:
- 不阻塞 DML 操作 (INSERT/UPDATE/DELETE)
- 仅阻塞 DDL 操作 (ALTER TABLE/DROP TABLE)
- 对业务影响更小

**使用条件**:
```go
if dbOpsContext.IsSupportBackupLock() {
    // 使用 LOCK INSTANCE FOR BACKUP
    runWithBackupLock()
} else {
    // 使用 FTWRL
    runWithoutBackupLock()
}
```

## 六、混合引擎场景

### 6.1 InnoDB + MyISAM 混合

**场景**: 数据库中同时存在 InnoDB 和 MyISAM 表。

**处理策略**:
```sql
-- 主线程
FLUSH TABLES WITH READ LOCK;          -- 统一锁住所有表

-- InnoDB 子线程
START TRANSACTION WITH CONSISTENT SNAPSHOT;  -- 建立快照

-- MyISAM 子线程
LOCK TABLES `myisam_tbl1` READ;       -- 各自锁表

-- 主线程
UNLOCK TABLES;  -- 释放全局锁,此时:
                -- ✅ InnoDB 受快照保护
                -- ✅ MyISAM 受表锁保护
```

**代码位置**: `dumper/dump/lockstill.go:50-100`

### 6.2 只有 InnoDB 表

**优化**: 如果数据库中只有 InnoDB 表,可以跳过 FTWRL,直接开启快照。

**判断逻辑**:
```go
if !hasMyISAMTables && !cfg.NeedConsistentBinlogPos {
    // 跳过 FTWRL,直接开启快照
    lockless = true
}
```

### 7.3 无锁模式特点

**执行流程**:
- ❌ 不执行 `FLUSH TABLES WITH READ LOCK`
- ✅ 仍然开启一致性快照 (`START TRANSACTION WITH CONSISTENT SNAPSHOT`)
- ⚠️ 风险: 全量期间的增量数据可能丢失 (依赖 binlog 补偿)

**适用场景**:
- 从备库导出数据
- 允许少量数据不一致
- 业务对锁非常敏感

## 八、InnoDB MVCC 原理

### 8.1 什么是 MVCC?

**MVCC (Multi-Version Concurrency Control)**: 多版本并发控制

**核心思想**:
- 每行数据维护多个版本
- 读操作读取特定版本,不阻塞写操作
- 写操作创建新版本,不阻塞读操作

### 8.2 Read View (读视图)

**定义**: 事务开始时创建的数据快照。

**创建时机**:
```sql
START TRANSACTION WITH CONSISTENT SNAPSHOT;
```

**Read View 包含的信息**:
- `m_ids`: 当前活跃的事务 ID 列表
- `min_trx_id`: 最小的活跃事务 ID
- `max_trx_id`: 系统下一个要分配的事务 ID
- `creator_trx_id`: 创建该 Read View 的事务 ID

### 8.3 可见性判断

**规则**:
```
对于数据行的某个版本 (trx_id):
1. 如果 trx_id < min_trx_id → 可见 (已提交)
2. 如果 trx_id >= max_trx_id → 不可见 (未开始)
3. 如果 trx_id in m_ids → 不可见 (活跃中)
4. 否则 → 可见 (已提交)
```

**示例**:
```
T0: 事务 A (trx_id=100) 开始,创建 Read View:
    m_ids = [100, 102, 105]
    min_trx_id = 100
    max_trx_id = 106

T1: 查询某行数据:
    版本1 (trx_id=99)  → 可见 (< min_trx_id)
    版本2 (trx_id=102) → 不可见 (in m_ids)
    版本3 (trx_id=106) → 不可见 (>= max_trx_id)
```

### 8.4 为什么 FTWRL 后可以释放锁?

**关键**: 一旦 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 执行完成,Read View 已经创建。

**后续读取**:
- 基于 Read View 读取数据,看到的都是 T1 时刻的快照
- 即使解除 FTWRL,后续的写操作创建新版本 (trx_id > max_trx_id)
- 新版本对当前事务不可见,保证一致性

## 九、MyISAM 表锁原理

### 9.1 为什么 MyISAM 需要表锁?

**原因**: MyISAM 不支持 MVCC,无法通过快照隔离。

**特点**:
- 读锁 (Shared Lock): 允许并发读,阻塞写
- 写锁 (Exclusive Lock): 阻塞读和写

### 9.2 LOCK TABLES 语法

**语法**:
```sql
LOCK TABLES 
  `db1`.`tbl1` READ,
  `db1`.`tbl2` READ,
  ...;
```

**效果**:
- 当前会话持有这些表的读锁
- 其他会话的写操作被阻塞
- 其他会话的读操作正常

### 9.3 解锁时机

**必须条件**: 数据导出完成。

**解锁方式**:
```sql
UNLOCK TABLES;
```

**注意**: 
- `COMMIT` 不会释放表锁 (MyISAM 不支持事务)
- 必须显式 `UNLOCK TABLES`

## 十一、故障恢复

### 11.1 场景 1: 主线程释放 FTWRL 前宕机

**状态**:
- 主线程持有 FTWRL
- 子线程未启动或部分启动

**影响**:
- FTWRL 会在连接断开时自动释放
- 数据库恢复正常写入

**恢复策略**:
- 重新启动 Dumper
- 重新执行加锁流程

### 11.2 场景 2: 子线程导出期间宕机

**状态**:
- FTWRL 已释放
- InnoDB 快照/MyISAM 表锁已建立
- 部分数据已导出

**影响**:
- InnoDB 快照随连接断开失效
- MyISAM 表锁自动释放

**恢复策略**:
- 读取 checkpoint,获取已导出的表列表
- 跳过已导出的表,继续导出剩余表
- 重新建立一致性快照 (新的 binlog 位点)

**代码位置**: `dumper/dump/mydumper.go:350-400`

## 十二、不同模式对比

### 12.1 加锁模式对比

| 模式 | 全局锁 (FTWRL) | InnoDB 快照 | MyISAM 表锁 | 适用场景 |
|------|---------------|------------|------------|---------|
| **有锁模式** | ✅ 加锁 → 建立快照 → 解锁 | ✅ MVCC 快照 | ✅ 持续表锁 | 生产环境,数据一致性要求高 |
| **无锁模式** | ❌ 不加锁 | ✅ MVCC 快照 | ❌ 不锁表 | 备库导出,允许少量不一致 |
| **备份锁模式** | 用 `LOCK INSTANCE FOR BACKUP` 替代 | ✅ MVCC 快照 | ✅ 表锁 | MySQL 8.0+,减少锁影响 |

### 12.2 锁持有时长对比

**FTWRL 持有时长**:
```
T0: FTWRL 加锁
T1: 子线程快照建立 (约 1-3 秒)
T2: 释放 FTWRL
持有时长: T2 - T0 ≈ 1-3 秒
```

**MyISAM 表锁持有时长**:
```
T1: LOCK TABLES
T4: 数据导出完成,UNLOCK TABLES
持有时长: T4 - T1 ≈ 数据导出时长 (可能数小时)
```

## 总结

### 核心流程

1. **主线程加 FTWRL** → 全局冻结数据库
2. **主线程开启快照** → 记录 binlog 位点
3. **子线程建立快照/表锁** → 各自保护数据一致性
4. **主线程释放 FTWRL** → 解除全局阻塞
5. **并发导出数据** → 基于快照/表锁读取数据

### 关键技术

| 机制 | InnoDB | MyISAM |
|------|--------|--------|
| **一致性保证** | MVCC Read View | 表级读锁 |
| **锁持有时长** | 事务期间 (自动管理) | 导出期间 (需显式解锁) |
| **并发影响** | 不阻塞写操作 | 阻塞写操作 |
| **适用场景** | 高并发 OLTP | 低并发/只读场景 |

### 最佳实践

1. **优先使用备份锁** (MySQL 8.0+)
2. **从备库导出** (减少对主库影响)
3. **开启无锁模式** (备库 + 允许不一致)
